Date: 2026-05-20
Dump: `docs/jkr-db/gems_jkr_staging_prod.sql`
Compared against: current dev database configured by `api/class/Constant.php` (`gems_jkr`; credentials redacted)

## Method

- Did not run destructive operations.
- Local MySQL was not running, so the dump was not imported.
- Parsed the dump offline for DDL and targeted config INSERT rows.
- Queried the current dev database read-only via `information_schema` and selected config tables.
- Compared the dump as target/prod snapshot against dev as the latest reference structure/config.

## Upgrade Decision

For this specific dump, no schema upgrade SQL is required to match the current dev structure.

Recommended action before client handoff:

1. Restore/import the dump into the target environment.
2. Ensure application environment constants point to the restored schema in both backend stacks:
   - `api/class/Constant.php`
   - `api/library/config.ini`
3. Run `docs/jkr-db/verify_gems_jkr_staging_prod_upgrade.sql` against the restored database.
4. If all verification rows show `PASS`, the DB structure and critical config are aligned with dev.

## Residual Risks

- This comparison confirms schema and selected critical config, not every business data row.
- `wfl_checkpoint_user` contains environment-specific user assignments; the dump has 13 extra assignment rows compared with dev, so user availability should still be smoke-tested with real client users.
- Workflow runtime execution tables differ by nature: the dump has `wfl_transaction=6`, `wfl_task=26`, and `wfl_task_assign=30`, while the current dev reference has `wfl_transaction=1`, `wfl_task=3`, and `wfl_task_assign=7`. These are active/history workflow execution records, not path configuration.
- Runtime permissions still matter. If debug logging is enabled, the PHP process must be able to write configured log paths or use the safe logging fallback already patched in the app.
